== STANDING RULE: put scratch/tmp files in PWD, not bare /tmp (2026-10-13)

This session repeatedly wrote ad hoc test/log files directly under `/tmp/`
(`/tmp/tk9-build-*.log`, `/tmp/settings-filtered*.sed`,
`/tmp/test-settings*.sh`, ...). Put these under the current working
directory instead (e.g. a scratch subdirectory, or just the repo's own
working dir) so they are easy to find again, do not collide with other
sessions'/users' same-named files in shared `/tmp`, and get cleaned up
along with the rest of the session's work rather than lingering in `/tmp`
indefinitely. Note this is distinct from genuine build scratch that
intentionally lives under `$TMP` by convention (e.g. `/tmp/distro`,
`/tmp/woz/*-B` conda roots per `dev/conda/*.sh`'s own `TMP=${TMP:-/tmp}`) --
those stay where the project's own scripts expect them.

== STANDING RULE: use conda-build.sh -C before a full build (2026-10-13)

`conda-build.sh -C` (configure-only) generates `meta.yaml` and
`settings.sed` and then stops -- no `conda build` invocation, no package
solve/download/compile/test. It is seconds instead of minutes.

Whenever iterating on `dev/conda/` files that affect `meta.yaml` or
`settings.sed` generation (SPEC_TK, deps.sh, settings.sed itself,
meta-template.yaml, pkgs-*.yaml, common.m4), run
`conda-build.sh -C [-r RV] PLATFORM BUILD_NUMBER` first and inspect the
generated `PLATFORM/settings.sed` -- and, critically, actually APPLY it
with `sed -f PLATFORM/settings.sed dev/build/swift-t-settings.sh.template`
and grep the result for the variables being changed (LAUNCHER, TCLSH, ...).
Generating the sed script is not enough to catch a bug: the 2026-10-13
LAUNCHER regression (`s@.*LAUNCHER=.*@&LAUNCHER=...@` silently landing
inside a `#`-commented line, so LAUNCHER was never actually set) only
showed up when the generated sed was actually run against the real
template, not just eyeballed or m4-filtered.

Only after that check looks right is a real `conda-build.sh PLATFORM N`
(no `-C`) worth spending the minutes on.

== STANDING RULE: always consider both platforms (2026-10-13)

`dev/conda/` supports exactly two platforms, `linux-64` and `osx-arm64`,
and several files are SHARED between them (`settings.sed`, `settings-R.sed`,
`meta-template.yaml`, `common.m4`, `conda-build.sh`, `conda-install.sh`).
A fix aimed at one platform's bug can silently change behavior, or crash
outright (e.g. zsh's NOMATCH-on-unmatched-glob), on the other.

Whenever proposing or making a change under `dev/conda/` (or anything else
that affects the conda build/install path, e.g. `turbine/code/configure.ac`,
shebangs, settings sed scripts), explicitly check its effect on BOTH
platforms before considering the change done:

* Is the touched file shared (`settings.sed`, `meta-template.yaml`, ...) or
  platform-specific (`linux-64/deps.sh`, `osx-arm64/deps.sh`, ...)?
* If shared: does the change rely on an assumption (a binary name, a glob
  match, a shell builtin's availability, GNU vs BSD tool flags) that may
  not hold on the other platform?
* osx-arm64 has its own accumulated tuning (`clang==18.1.8` pin, the
  tk strstr two-level-namespace bug/build-string pin, `USE_GCC=0`,
  `SPEC_MPICH='mpich==4.1.2'`) that a linux-focused fix must not regress.
* When unsure whether a shared-file change is safe on the other platform,
  say so explicitly rather than assuming "it probably also works there".

See the `TCLSH` glob fix (2026-10-13 section below) for a concrete example:
the first draft used `$(ls $PREFIX/bin/tclsh[0-9]*)`, which would hard-crash
under zsh (not just error) if the glob ever failed to match on EITHER
platform; the `(N)` zsh glob qualifier was added specifically to make that
failure mode safe cross-platform.

== Problem

Jenkins build failed at the `swift-t -E 'trace(42);'` test with:

----
couldn't load file ".../swift-t/turbine/lib/libtclturbine.so":
/lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found
(required by .../libtclturbine.so)
    while executing "load .../libtclturbine.so"
    ("package ifneeded turbine 1.5.2" script)
    invoked from within "package require turbine 1.5.0"
----

(The accompanying `libtinfow.so.6: no version information available` warnings
from zsh are a harmless symptom of the same conda-vs-host library mismatch,
not the failure.)

== Root cause

`libtclturbine.so` was *compiled* against the build host's **system glibc
(2.38)** instead of an older conda sysroot. When the built package is then
installed and tested on a host with glibc < 2.38, the dynamic loader cannot
resolve the `GLIBC_2.38` symbol versions, so the Tcl `load` fails and cascades
to `package require turbine`.

The recipe pulled in the bare `- gcc` metapackage, which does NOT reliably
activate a sysroot. The exact `GLIBC_2.38` requirement (the newest symbol
version on the builder) is the signature of "linked against the host libc".

This is the same class of problem as the GLIBCXX / libstdc++ issue the
project had already been fighting on GCE Jenkins
(see `dev/conda/conda-install.sh:139-148` and the "New Jenkins attempt" /
"Try plain GCC on Jenkins: 2026-10-09" changes).

== Recommended approach (conda, Linux)

Use the conda compiler-activation functions in the recipe rather than a bare
compiler metapackage:

[source,yaml]
----
requirements:
  build:
    - {{ compiler('c') }}
    - {{ compiler('cxx') }}
----

These expand to `gcc_linux-64` etc. and drag in `sysroot_linux-64`, setting
`CC`/`CFLAGS`/`CONDA_BUILD_SYSROOT` to the cos7 / glibc-2.17 sysroot. This is
the officially recommended idiom on BOTH conda-forge and Anaconda `defaults`.
Runtime libs (`libgcc-ng`/`libstdcxx-ng`) are added automatically via the
compilers' run-exports, so they belong in `build:` only, not `run:`.

Manually adding `gcc` + `sysroot_linux-64` is only a fallback for when the
jinja compiler functions cannot be used.

=== osx-arm64 note

macOS has no glibc; the equivalent portability floor is the **macOS SDK +
deployment target** (`LC_BUILD_VERSION` / `minos`), also provided by
`{{ compiler('c') }}` (which resolves to `clang_osx-arm64` there).

DECISION (this session): leave osx-arm64 as-is. Its `deps.sh` carefully pins
`clang==18.1.8` ("Prevent MPICH from updating Clang to 19") and documents the
`tk`/`strstr` two-level-namespace work. Switching to `{{ compiler() }}` would
drop the inline clang version pin (version would come from conda variant
pinnings) and risk regressing that work — and osx doesn't have the glibc bug
anyway. Fix applied to the gcc/linux path only.

== m4 gotchas (snippet authoring)

These bit us while editing the pkgs-*.yaml snippets. Each snippet is pulled
into `meta-template.yaml` as the THIRD argument of `m4_ifelse(...)`:

  m4_ifelse(m4_getenv(USE_GCC), `1', m4_include(pkgs-gcc.yaml))m4_dnl

That context imposes two rules on snippet CONTENT (payload *and* comments):

1. NO COMMAS. A comma inside the included text is seen by m4 as an argument
   separator for `m4_ifelse`, so everything after the first comma is treated
   as excess arguments and dropped. Symptom seen this session:
     m4:.../meta-template.yaml:44: Warning: excess arguments to builtin
     `m4_ifelse' ignored
   The generated `meta.yaml` was truncated mid-comment, the `- {{ compiler(...) }}`
   lines were LOST, snippets ran together, and a literal `m4_dnl` leaked into
   the output. Fix: rewrote the comments in `pkgs-gcc.yaml` / `pkgs-zlib.yaml`
   to use ` -- ` and periods instead of commas. (The pre-existing snippets
   only worked because their comments happened to be comma-free.)

2. SINGLE QUOTES are m4 quote chars. Use DOUBLE quotes inside payload, e.g.
   `{{ compiler("c") }}` not `{{ compiler('c') }}`. Double quotes are valid
   jinja and pass through m4 untouched; a stray `'` unbalances m4 quoting.

Each snippet now carries a NOTE comment restating rule 1 so future edits do
not reintroduce the comma bug.

Verification that catches both: simulate the real inclusion rather than
filtering the snippet directly (direct filtering does NOT trigger the comma
bug because there is no enclosing m4_ifelse):

[source]
----
printf '%s\n' \
  'm4_ifelse(m4_getenv(USE_GCC),  `1'\'', m4_include(pkgs-gcc.yaml))m4_dnl' \
  'm4_ifelse(m4_getenv(USE_ZLIB), `1'\'', m4_include(pkgs-zlib.yaml))m4_dnl' \
  > /tmp/m4test.m4
USE_GCC=1 USE_ZLIB=1 m4 -P -I . common.m4 /tmp/m4test.m4   # expect: no warning
----

== Downstream fixes discovered while validating the build

Switching to the sysroot compilers let the build proceed far enough to
expose a chain of further issues (all pre-existing, surfaced by modern
conda-build's separate `_build_env`).  Each was fixed; the linux-64
`conda build` now passes end to end, including the test that originally

=== 4. mpicc exit 127 (stale cos6 backend)

`{{ compiler("c") }}` installs `x86_64-conda-linux-gnu-cc`, but the
`mpich-mpicc` wrapper defaulted to the stale `x86_64-conda_cos6-linux-gnu-cc`
backend (not installed) -> `command not found` -> exit 127.
FIX (`dev/conda/build-generic.sh`, linux branch): export
`MPICH_CC=${CC}` / `MPICH_CXX=${CXX}` (mirrors the osx-arm64 clang branch).

=== 5. MPI_IMPL=UNKNOWN (ancient mpich pulled)

Unpinned `mpich-mpicc` let the solver pull mpich 3.2.1, whose `mpi.h`
predates `MPICH_API_PUBLIC` - the only token Turbine's
`maint/mpi_identification.c` checks - so MPI detection failed:
`#error "Must specify MPI_IMPL!"`.
FIX (`dev/conda/linux-64/deps.sh`): `export SPEC_MPICH='mpich-mpicc=4.3.2'`
(4.x/5.x define `MPICH_API_PUBLIC`).  osx-arm64 already pins `mpich==4.1.2`.

=== 6. stc: Cannot run java! (baked build-env Java path)

`stc-config.sh` baked `USE_JAVA=$(which java)` = the build-env Java, and
its Conda re-resolution was gated on that path being MISSING - but
`conda build --dirty` keeps `_build_env` on disk, so the stale path
persisted and an unrunnable Java was used.  It also derived the prefix from
`${CONDA_EXE:h:h}` (the base env, which had no java) instead of the active
env.
FIX (`stc/code/etc/stc-config.sh`, SOURCE): under Conda, always resolve
Java from the active environment, in order: `$CONDA_PREFIX/bin/java`, then
`command -v java` (PATH), then the base env via `CONDA_EXE` incl. its
`pkgs/openjdk-*` cache; keep the build-time path only as last resort.
Result: `Using Java VM: $PREFIX/bin/java`.

=== 7. Baked build-env tool paths in turbine-config.sh (launcher/tclsh/python)

Installed `turbine-config.sh` baked `_build_env` paths for the launcher,
tclsh, mpicc and python.  The launcher was fatal (Turbine execs it):
`turbine/bin/turbine:362: no such file or directory: .../_build_env/bin/mpiexec`.
Root cause: those tools were only `build:` deps (-> `$BUILD_PREFIX`, which
Conda does NOT relocate and which is gone at run time).  Turbine's
`configure.ac` also `AC_CHECK_FILE`s the launcher, so it must exist at
build time - which, without a host prefix, forced the build-env path.
Separately, `libtclturbine.so` linked `libtcl8.6.so` but tcl was never a
declared dependency (conda-build warned the DSO was not found in packages).

FIX (the canonical conda build/host split):
* `dev/conda/meta-template.yaml`: added a `host:` section (python,
  openjdk, mpich, zlib, ncurses, tk, R) so these land in `$PREFIX` at
  build time and Conda relocates them into the install env.
* `dev/conda/settings.sed`: set `LAUNCHER=$PREFIX/bin/mpiexec` and
  `TCLSH=$PREFIX/bin/tclsh8.6` (the author's existing TODO) - now valid
  because the host section puts them in `$PREFIX`.
* `dev/conda/linux-64/deps.sh`: `USE_TK=1`, `SPEC_TK='tk'` to declare
  tcl/tk explicitly (tk provides `tclsh8.6` + `libtcl8.6.so`).
Result: `Using Turbine MPI launcher: $PREFIX/bin/mpiexec`, no missing-DSO
warning, test passes.  Package build string gains `py311` (correct: adding
python to host makes it a Python-ABI-specific build).

=== build/host/run distinction (why this works)

* build: tools run ON the build machine (compilers, make, ant) -> $BUILD_PREFIX, NOT relocated.
* host:  libs/tools linked/run against -> $PREFIX, present at build, Conda RELOCATES them.
* run:   what the user needs at runtime (often auto via run-exports).
Baked absolute paths are only relocatable when they point into the host
$PREFIX; anything in $BUILD_PREFIX (the `_build_env`) breaks at run time.

== 8. conda-install.sh: installed package failed to load (python ABI mismatch)

Installing the built PKG with `conda-install.sh` into a fresh env succeeded,
but running it failed:
  couldn't load libtclturbine.so: libpython3.11.so.1.0: cannot open shared
  object file
Cause: `conda-install.sh` had `SPEC_PYTHON="python"` (UNPINNED).  A fresh
env got Python 3.15, but the PKG is py311 (libtclturbine.so links
libpython3.11.so.1.0).  `conda install <file.conda>` does NOT enforce the
package's own python pin, so the mismatch slipped through.  libtcl8.6.so and
libmpi.so.12 were present (tk + mpich OK); only libpython was missing; the
RPATH (`$ORIGIN/../../../lib` = `$PREFIX/lib`) was correct.
FIX (`dev/conda/conda-install.sh`): derive the ABI from the PKG name
(`...-py311...` -> `python=3.11`) and pin SPEC_PYTHON to it.
RESULT: fresh-env install + `swift-t -E 'trace(42);'` -> `trace: 42`,
Python 3.11.17.  Validated end to end.

Note: conda-install.sh builds LIST without checking USE_ZLIB, so zlib is not
added explicitly (it came in transitively; harmless here).

=== 9. python-in-PATH warning (baked build-env python) - FIXED

The installed package printed:
  turbine: warning: python in PATH does not match the Python used at compile
  time   compiled with: .../_build_env   found in PATH: .../envs/.../bin/python
Turbine baked the build-env python DIRECTORY (TURBINE_USE_PYTHON).  Non-fatal
(the 3.11 ABI matches so libpython loads), but the same _build_env smell.

First attempt (`PYTHON_EXE=$PREFIX/bin/python` via `s@PYTHON_EXE=""@...@`) did
NOT work: `swift-t-settings.sh` has no uncommented `PYTHON_EXE=""` line to
anchor on (only commented examples), so the sed never matched.  Turbine's
configure then got `--enable-python` (not `--with-python-exe`) and
auto-detected `$BUILD_PREFIX/bin/python` (configure: `checking for python...
$BUILD_PREFIX/bin/python`).  The launcher/tclsh worked only because they were
appended after the matching `MPI_VERSION` anchor.

FIX (`dev/conda/settings.sed`): append PYTHON_EXE after the matching
ENABLE_PYTHON anchor:
  s@ENABLE_PYTHON=0@ENABLE_PYTHON=1\nPYTHON_EXE="$PREFIX/bin/python"@
Now build-turbine.sh passes `--with-python-exe=$PREFIX/bin/python`, turbine
bakes `$PREFIX/lib` (configure: `using Python: $PREFIX/lib python3.11`), and
Conda relocates it.  Validated on build 5: conda-build test has ZERO
python-mismatch warnings, and a fresh-env conda-install + `trace(42)` ->
`trace: 42` with no warning.

Lesson: settings.sed `s@VAR=""@...@` only works where swift-t-settings.sh has
that exact uncommented line; otherwise append after a known-present anchor
(ENABLE_PYTHON, MPI_VERSION).

Note: a stray `can't find package pt::pgen 1.0.3 (/usr/bin/pt)` appears at
runtime - that is a SYSTEM Tcl parser-tools binary on PATH, unrelated to the
package; `trace: 42` still succeeds (exit 0).  Benign.

== R-enabled build: RInside linked against the wrong R (2026-10-12)

`dev/conda/conda-build.sh -r 4.4 linux-64 4` (first time the `-r` /
`ENABLE_R` path was actually exercised) failed its test phase:

  couldn't load file ".../turbine/lib/libtclturbine.so":
  libRInside.so: cannot open shared object file: No such file or directory

Root cause: `r=VERSION` is listed in the `build:`, `host:`, and `run:`
sections of `pkgs-R.yaml`/`meta-template.yaml`. During the build,
`$BUILD_PREFIX/bin` is ahead of `$PREFIX/bin` on `PATH`, so any lookup that
just does `which R` / `which Rscript` silently resolves to the *build*
environment's R, not the host R that actually gets packaged/relocated.
Two separate places did this and both had to be fixed:

=== 9a. build-generic.sh RInside install - FIXED

`build-generic.sh` ran `which R` / `R RHOME` / `Rscript` to build and
`install.packages("RInside")` into whatever R that found. It found
`$BUILD_PREFIX/lib/R`, so RInside got compiled and installed into the
ephemeral build env -- discarded after the build, never shipped in the
package -- instead of the host `$PREFIX/lib/R` that ships and gets tested.

FIX: use `$PREFIX/bin/R` / `$PREFIX/bin/Rscript` explicitly instead of
`which`/bare `R`/`Rscript`, so RInside installs into the host R and is
packaged.

=== 9b. settings-R.sed R_INSTALL anchor - FIXED

Same anchor trap as the earlier `PYTHON_EXE` issue (9): `settings-R.sed` had
`s@R_INSTALL=.*@R_INSTALL="$R_HOME"@`, but `swift-t-settings.sh` has no
uncommented `R_INSTALL=` line to match (only a commented example), so the
substitution silently no-opped and `R_INSTALL` was never set. Without it,
`build-turbine.sh` passes `--enable-r` instead of `--with-r=$R_INSTALL`, and
turbine's `configure` finds R via plain `which Rscript` -- same
`$BUILD_PREFIX`-shadowing problem as 9a, this time baked into
`libtclturbine.so`'s link path.

FIX (`dev/conda/settings-R.sed`): append `R_INSTALL` after the `ENABLE_R`
anchor, like `PYTHON_EXE`:
  s@ENABLE_R=0@ENABLE_R=1\nR_INSTALL="$R_HOME"@
`$R_HOME` is exported by build-generic.sh (from `$PREFIX/bin/R RHOME`) and
expanded when `swift-t-settings.sh` is sourced at build time.

Both fixes were needed together -- fixing only 9a still left turbine's own
`configure` resolving R via `$BUILD_PREFIX`. Validated end-to-end on build 4:
`swift-t-r-1.6.9-py311r44h3fd9d12_4.conda` built, test phase prints
`trace: 42` with no `libRInside.so` error (the unrelated stray
`pt::pgen` message from note 9 still appears and is still benign).

Lesson: any "effective PATH / env var" anchor trick (`which TOOL`, an
`s@VAR=.*@...@` sed that depends on an uncommented line already existing)
should be treated as suspect wherever `$BUILD_PREFIX` and `$PREFIX` both
provide the same tool -- check both spots, not just the one that first
errors.

== conda-install.sh printf argument-collapsing bugs (2026-10-12)

`./conda-install.sh -r /tmp/.../broken/swift-t-r-...4.conda` reported
`size: 0.0 MB` instead of the real size.

=== 10a. msgf/failf "${*}" bug - FIXED

`msgf()`/`failf()` did `printf "${*}"`, which joins all arguments (format
string plus values) into ONE string before handing it to `printf`. With only
one argument left, `printf`'s `%s`/`%.1f` specifiers inside it have nothing to
consume and silently default to empty/`0` -- hence `size: 0.0 MB`.

FIX (`dev/conda/conda-install.sh`): use `"${@}"` instead of `"${*}"` in both
`msgf` and `failf`, preserving the format string and each value as separate
`printf` arguments. Verified: re-running the same command now correctly
prints `size: 8.3 MB`.

=== 10b. abortf() same bug pattern - FIXED (latent, no bad caller yet)

=== Root cause

`dev/conda/conda-install.sh:149-157` intentionally pins
`SPEC_TK="tk=8.6.13"` for linux-64 + Python 3.14 (Python 3.14 otherwise
pulls Tcl/Tk 9.0, but the package was built against 8.6 and Turbine's
`turbine-config.sh` hardcodes `TCLSH=$PREFIX/bin/tclsh8.6` via
`settings.sed`). But `conda-install.sh` then sources
`dev/conda/linux-64/deps.sh`, which did `export SPEC_TK='tk'`
unconditionally -- silently overwriting the 8.6.13 pin. The solver then
picked `tk-9.0.4` (confirmed in the log's install package-plan), whose
shell binary is `tclsh9.0`, not `tclsh8.6` -- the missing-file error above.

Same anchor/override-ordering footgun as notes 9/9b above (a later,
more-general step clobbering an earlier, more-specific one).

=== Fix 1: stop deps.sh from clobbering a caller-set pin

`dev/conda/linux-64/deps.sh`: `export SPEC_TK='tk'` ->
`export SPEC_TK=${SPEC_TK:-tk}`. Falls back to the old unpinned default
everywhere `SPEC_TK` isn't already set (`conda-build.sh`'s build-time path,
which never pre-sets it), but preserves `conda-install.sh`'s Python-3.14
pin instead of overwriting it.

=== Packaging fix, part 2: make TCLSH version-agnostic (towards allowing Tcl 9)

Turbine's own `configure.ac:845` already derives the Tcl shell name from
`tclConfig.sh`'s `$TCL_VERSION` (`tclsh$TCL_VERSION`) -- it is NOT hardcoded
to 8.6. The 8.6 pin is purely a conda-packaging workaround. To stop forcing
8.6 forever (and make a future Tcl 9 package "just work" once verified):

* `dev/conda/settings.sed`: `TCLSH=$PREFIX/bin/tclsh8.6` (hardcoded) ->
  derived at build time from whatever `tclshN.N` the host `tk` package
  actually provides:
----
s@^MPI_VERSION=.*@&\nLAUNCHER=$PREFIX/bin/mpiexec@
s@^LAUNCHER=.*@&\nTCLSH=$PREFIX/bin/tclsh[0-9]*(N)@
----
  (Split into two single-variable `s@@` commands, each anchored off the
  previous inserted line -- same style as the existing `ENABLE_PYTHON` ->
  `PYTHON_EXE` anchor trick in the same file. A plain zsh glob is used
  instead of `ls`/`sort`/`tail`, since only one `tk` package/version is
  ever installed into host: at once; the `(N)` ("nullglob") qualifier is
  REQUIRED because this file is sourced by zsh, which by default aborts
  the whole build with "no matches found" on an unmatched glob -- without
  it, a glob miss on EITHER platform would be a hard crash instead of an
  empty `TCLSH`. This file is shared by linux-64 AND osx-arm64 -- see the
  standing cross-platform rule at the top of this document.)

* `dev/conda/pkgs-tk-run.yaml` (NEW) + `dev/conda/meta-template.yaml`:
  the `run:` section's `tk` requirement now uses
  `{{ pin_compatible("tk") }}` instead of including the plain
  `pkgs-tk.yaml` (bare `- m4_getenv(SPEC_TK)`). `build:`/`host:` still use
  `pkgs-tk.yaml` unchanged. Rationale: an unpinned `tk` in `run:` is a
  SEPARATE solve from `host:` at install/test time and can drift to a
  newer `tk` than what was actually linked into `libtclturbine.so` --
  exactly how the install step above independently got `tk-9.0.4` while
  the build got `tk==8.6.13`. `pin_compatible("tk")` ties `run:` to the
  version conda-build actually resolved into `host:`, whatever that
  version is (8.6 or a future 9.0).

Together these two changes make the TCLSH/tk plumbing version-agnostic:
whichever `tk` `SPEC_TK` resolves to, `TCLSH` and the run pin follow it
automatically, instead of three separate hardcoded/independently-solved
8.6 references needing to be kept in sync by hand.

=== Settings.sed cleanup: each sed rewrites its OWN variable's line

First draft of the `TCLSH` fix chained two `s@@` commands: insert `LAUNCHER`
right after the `MPI_VERSION=` line, then insert `TCLSH` right after that
newly-inserted `LAUNCHER` line (via `&\n...` append). This works but is
needlessly confusing -- it reads as "replacing MPI_VERSION with LAUNCHER".
Checked `dev/build/swift-t-settings.sh.template.conda` and found it already
has real, UNCOMMENTED default lines for both ("For Anaconda, use ... from
PATH"): `TCLSH=tclsh8.6` and `LAUNCHER=mpiexec`. So the append/chain trick
(needed for `PYTHON_EXE`/`R_INSTALL`, which have no uncommented anchor) was
never needed here. Simplified to two independent, self-anchored rewrites:
----
s@^LAUNCHER=.*@LAUNCHER=$PREFIX/bin/mpiexec@
s@^TCLSH=.*@TCLSH=$PREFIX/bin/tclsh[0-9]*(N)@
----
Each line now does exactly one thing: rewrite the value already assigned to
that variable. Lesson: before reaching for the append-after-anchor trick
(justified for `PYTHON_EXE`/`R_INSTALL`/`ENABLE_*`), check whether the
target template already has an uncommented default line to rewrite
directly -- simpler and far less confusing to read.

=== Bug 2 (recurrence prevention): file-list.zsh swept up generated files

Root-caused WHY the stale `blob_wrap.c` got packaged at all:
`turbine/code/maint/file-list.zsh` had
`print **/*.[cChi] **/*.{tcl,swift}` -- a glob with no way to distinguish

FIX (`turbine/code/maint/file-list.zsh`): added `setopt extendedglob` and

a synthetic `touch .../blob_wrap.c; file-list.zsh | grep wrap` -> no

=== Bug 3 (my own regression): rewrote the wrong template's lines

After Bug 1/2 fixes, "simplified" `settings.sed`'s `TCLSH`/`LAUNCHER`
handling from an append-after-`MPI_VERSION` anchor to direct in-place
rewrites (`s@^LAUNCHER=.*@LAUNCHER=...@`), reasoning that
`dev/build/swift-t-settings.sh.template.conda` already has uncommented
default lines for both. WRONG: `init-settings.sh` actually copies
`swift-t-settings.sh.template` (no `.conda` suffix) -- the `.conda` file
is unused/dead and happens to look similar. The real template has NO
uncommented `LAUNCHER=`/`TCLSH=` line (only commented examples, and
`TCLSH_LOCAL=`, a DIFFERENT variable name than the `TCLSH` that
`build-turbine.sh` actually checks), so the anchored rewrite matched
nothing and both variables silently stayed unset.

LESSON: before rewriting a sed anchor, verify which template file is
actually consumed at runtime (`grep -rn template dev/build/init-settings.sh`),
not just "a file that looks like the right one".

Reverted to append-after-anchor, which surfaced a second, independent sed
subtlety: two separate `s@^LAUNCHER=.*@&\n...@` / `s@^TCLSH=.*@&\n...@`
commands CANNOT be chained (anchoring the second on the line the first one
just inserted) -- sed's `^`/`.*` anchor to the start of the whole pattern
space and do not cross an embedded `\n` inserted earlier in the SAME
cycle, so the second command never matches and silently appends nothing.
Verified empirically with a real `sed -f` test rather than reasoning about
it abstractly. FIX: anchor both independently on the same original
`MPI_VERSION=3` line (each re-matches the still-intact original text,
since `.*` does not cross the newline the other command inserted).

=== Bug 4 (my own regression): assumed the wrong shell

Also assumed `swift-t-settings.sh` is sourced by zsh (since it lives under
`dev/conda/` next to zsh scripts) and used a zsh glob qualifier,
`TCLSH=$PREFIX/bin/tclsh[0-9]*(N)`. WRONG: it is actually sourced by
`dev/build/build-swift-t.sh`, which is BASH (`#!/usr/bin/env bash`,
`set -eu`). `(N)` is a bash syntax error
(`syntax error near unexpected token '('`) -- confirmed directly in a
build log, not assumed. Also, bash does not glob-expand the right-hand
side of a plain variable assignment at all (unlike zsh), so even a bare
`tclsh[0-9]*` would not dynamically resolve a binary in bash -- it needs a
command substitution so the glob expands as a command ARGUMENT. FIX: use
`TCLSH=$(ls $PREFIX/bin/tclsh[0-9]* 2>/dev/null | head -n1)`, with
`head -n1` deliberately as the pipeline's LAST stage so a glob miss (`ls`
exits non-zero) still leaves the overall substitution's exit status at 0
under `set -e` (this bash script has no `pipefail`, unlike the zsh caller
that generates it, so only the last pipeline stage's exit status counts).
Verified by actually sourcing the generated file under real bash with
`set -eu` before re-running the conda build.

LESSON (both bugs 3 and 4): do not assume a script's shell/behavior from
its directory or neighboring files -- trace the actual invocation chain

=== USE_TCLSH indirection (final design, user-driven)

The final design moved the TCLSH-resolution snippet out of `settings.sed`
and into `conda-build.sh`, exported as a shell variable consumed via
`m4_getenv`:
* `dev/conda/conda-build.sh`: `export USE_TCLSH='TCLSH=$(ls $PREFIX/bin/tclsh[0-9]* 2>/dev/null | head -n1)'`
  (single-quoted in zsh so `$PREFIX`/`$(...)`/the glob stay LITERAL text at
  export time -- they are only meant to execute later, when bash actually
  sources the generated `swift-t-settings.sh` at build time).
* `dev/conda/settings.sed`: `s@.*TCLSH=.*@m4_getenv(USE_TCLSH)@` -- matches
  the (user-added) commented template line `# TCLSH=/usr/bin/tclsh8.6` and
  replaces the WHOLE line (no `&`, so the `#` is discarded) with whatever
  `USE_TCLSH` holds, verbatim.
* `dev/conda/settings.sed`: `s@.*LAUNCHER=.*@LAUNCHER=$PREFIX/bin/mpiexec@`
  and `s@.*PYTHON_EXE.*@PYTHON_EXE="$PREFIX/bin/python"@` -- same
  whole-line-replacement pattern (leading `.*` consumes the `# ` prefix
  too), fixing two more silent-no-op bugs found via the same "apply the
  sed to the real template" verification step: an earlier draft used `&`
  (preserving the matched `#...` text) or an anchor without a leading
  `.*`, both of which left the `#` intact so the variable was never
  actually uncommented/set.

== Scratch/log files belong under PWD, never under /tmp or dotfiles (ongoing convention)

Repeated requirement across this session's build/install/regenerate steps:
any throwaway file this work produces -- build logs, install logs, one-off
test scripts -- goes into a plain, non-hidden subdirectory under the current
working directory (e.g. `dev/conda/tmp-logs/`, `dev/release/tmp-logs/`), never
under `/tmp` directly and never under a dot-prefixed directory.

Why this matters here specifically (not just a style preference):

* `/tmp` is shared, system-wide scratch space already used for OTHER
  purposes in this project's own workflow (the conda build root, the distro
  export snapshot -- see the note above). Dropping ad hoc log/test files
  there risks colliding with or being mistaken for those real build
  artifacts, and makes it easy to lose track of what is safe to delete.
* Logs and intermediate files kept under the repo's working directory (in a
  plainly-named, gitignore-able subdirectory) stay visible in normal
  directory listings and are easy for a reviewer -- human or otherwise -- to
  find later, unlike files tucked into `/tmp` or a dotfile that most tools
  and casual `ls` will not surface.
* This mirrors a mistake pattern seen elsewhere this session (note 11a/11b
  and the distro-snapshot note above): state living outside the obviously
  inspected locations is exactly what made two different staleness bugs hard
  to diagnose. Keeping scratch output in an obvious, PWD-relative spot keeps
  the same failure mode from recurring for logs themselves.

Applied this session: `dev/conda/tmp-logs/conda-build{5,6}.out`,
`dev/conda/tmp-logs/conda-install{5,6}.out`, and
`dev/release/tmp-logs/make-release-pkg*.out` were all written under their
respective command's own working directory rather than to `/tmp` or a
dotfile, including after an explicit correction mid-session when a command
was first drafted to log to `/tmp`.

=== 12. Corrupt conda package cache: R rewrites packages.html through the hardlink

Platform: osx-arm64 only (trigger is our `emews-r` package's R regenerating
`packages.html`).  The shared-cache *concurrency* amplifier below is a
general conda hazard, but the packages.html trigger itself is emews-r/mac.

`install_emews.sh` reported success, but the final "Installing R package
dependencies" step had crashed and none of the R packages
(`coro jsonlite purrr logger remotes`) were installed.  Verify R packages
directly (`Rscript -e 'rownames(installed.packages())'` or `LOAD OK: [N/N]`
in the log) rather than trusting the banner.

Root cause: conda installs cache files into the env as *hardlinks* (shared
inode).  R regenerates `lib/R/doc/html/packages.html` at runtime when
packages are installed, and that write propagates back through the hardlink
and mutates the integrity-tracked copy in the conda cache
(`~/conda-cache`).  The next conda transaction then trips
`SafetyError: ... emews-r ... appears to be corrupted` on `packages.html`,
and the broken/partial transaction leaves `libomp.dylib` misplaced, so R
dies at load with `dyld: Library not loaded: @rpath/libomp.dylib` and the
R-package step never runs.  The ~20 `ClobberError`s (tk vs xorg, see note
13) are collateral from the same broken transaction.

Fix: a helper, `emews-tutorial/code/install/clean_conda_cache.py`, scans the
cache and removes any extracted package whose files no longer match its
`info/paths.json` (the same size/sha256 data conda's SafetyError uses).
Important: it content-verifies `path_type: hardlink` entries only; softlink
entries store the size/sha of their *target* (may be absent in a bare
cache), so it only checks the link exists via `os.path.lexists` -- a naive
`os.path.exists` follows the link and yields hundreds of false positives on
normal packages.  Safe to delete cache copies hardlinked into a live env:
the env keeps its own inode; conda re-downloads a clean copy.  This bug
*recurred* later in the session on `emews-r-9` during the swift-t build
(same packages.html size mismatch); same fix.

Shared-cache concurrency amplifier (general conda hazard, not mac-specific
by itself, but it is what makes the mac/emews-r trigger bite repeatedly):
`~/.condarc` sets a single global `pkgs_dirs` (`/Users/woz/conda-cache`)
shared by all ~11 Miniconda roots on this machine
(`/private/tmp/woz/3NN-{B,T,R}`, `~/sfw/Miniconda-313-Main`).  conda assumes
one transaction at a time per `pkgs_dirs`; its locks are per-root, not
per-cache, so they do NOT coordinate across installations.  Running builds
from different Minicondas *concurrently* against the one cache can therefore
(a) corrupt via the shared hardlinked inode -- one build's R rewrites
`packages.html` while another is verifying that same cache entry -- and
(b) hit extract/verify races.  A build that is itself correct can fail this
way.  If concurrent builds are needed, give each root its own cache via
`CONDA_PKGS_DIRS` (e.g. `$ROOT/pkgs`) instead of the global `pkgs_dirs`;
otherwise serialize the builds.

=== 13. tk vs xorg-xorgproto ClobberErrors are expected, not corruption

Platform: osx-arm64 only (seen during `emews-r` transactions).

Separately from note 12, every emews-r transaction logs ClobberErrors for
shared `include/X11/*.h` headers (`X.h`, `Xlib.h`, `keysym.h`, ...).  Both
`tk` and `xorg-xorgproto` ship these headers.  This overlap exists *within*
conda-forge too (tk and xorg-xorgproto both from conda-forge still clobber),
so it is NOT a channel-mixing artifact.  conda's default `path_conflict`
policy treats these as warnings and picks a winner (last writer wins), so
the transaction succeeds.  They are only fatal when they land inside an
already-broken transaction (note 12).  Otherwise ignore them.

Also note: on osx-arm64 `tk>=8.6.15` resolves only from `defaults`
(conda-forge jumps 8.6.13 -> 9.0.4, no 8.6.15), so the env legitimately
mixes channels.  Documented in `dev/conda/README.adoc` (Dependencies: tk).

=== 14. emews-r FLIBS baked a stale gfortran version -> -lemutls_w

Platform: osx-arm64 only (FLIBS is baked into our `emews-r`; Linux uses the
community `r` with its own consistent toolchain).

`test-swift-t.sh 3.13` failed compiling R graphics packages (`nlme`,
`Matrix`, `mgcv`) with:
----
ld: warning: directory not found for option '-L.../lib/gcc/.../15.1.0'
ld: library not found for -lemutls_w
----
Root cause: R's `lib/R/etc/Makeconf` records `FLIBS` with an absolute,
version-pinned gcc lib dir detected at emews-r build time
(`.../lib/gcc/arm64-apple-darwin20.0.0/15.1.0`).  emews-r's recipe left
`gfortran` *unpinned*, so a later install pulled gfortran 16.2.0 while FLIBS
still pointed at the nonexistent 15.1.0 dir.

Fix: pin `gfortran 16.2.*` in both `build:` and `run:` in emews-r's
`meta.yaml`, bump emews-r 8 -> 9, rebuild.  emews-r is python-independent
(no python in depends, build string is just the build number), so ONE
osx-arm64 build serves Python 3.11-3.14; the real drift axis is time (conda-
forge bumping gfortran), not Python.  Verified: the rebuilt package's
Makeconf FLIBS reads 16.2.0 with zero 15.1.0.

Related: Python does NOT require gcc compatibility -- conda Python is a clang
world (CC=clang, links libSystem, no libgfortran).  gfortran only matters
for Fortran code (R's numeric packages; numpy/scipy if present), and conda
coordinates that via libgfortran5 run_exports, independent of Python.
HOWEVER swift-t (Turbine) DOES embed a specific `libpython3.XY.dylib`, so
swift-t itself is python-tagged and needs a build per Python minor -- unlike
emews-r.

=== 19. eq-r's unpinned tk -> solver downgrades swift-t-r -> _strstr crash

Platform: osx-arm64 only (the bad `tk 8.6.13` strstr build and our custom
swift-t-r/eq-r builds are osx-arm64; the fix is in eq-r's osx-arm64 recipe).

A GitHub run (`gh.txt`, osx-arm64 PY=3.13) pulled the RIGHT emews-r
(`emews-r-9-1` -- note 17's fix worked) but still crashed at
`swift-t -E 'trace(...)'`:
----
dlopen(.../turbine/lib/libtclturbine.dylib): Symbol not found: _strstr
  Expected in: .../lib/libtcl8.6.dylib
----
This is the `tk==8.6.13` two-level-namespace `strstr` bug already known from
swift-t's build (see notes at lines ~59/134 and `dev/conda/osx-arm64/deps.sh`,
which pins `tk>=8.6.15` for exactly this reason).  Here it reappeared at
INSTALL time, from a different layer.

Root cause (a build-number DOWNGRADE trap, distinct from notes 16/17's
version pins): GitHub installs `eq-r=1.3`, whose recipe
(`EQ-R/<pyver>/conda/pkgs-tk.yaml`) declares a bare, unpinned `- tk`, and
whose `meta-template.yaml` pins only `swift-t-r==<version>` (no build
number).  With tk free to be `8.6.13`, conda finds a self-consistent
LOWER-build solution -- `swift-t-r-1.6.9-py313_3` (which itself requires
`tk 8.6.13`) + `tk-8.6.13` -- instead of climbing to the newest
`swift-t-r py313_6` (which requires `tk>=8.6.15`).  `tk 8.6.13` is the
strstr-poisoned build, hence the runtime crash.  Reproduced deterministically
off-CI: `conda create ... eq-r=1.3 emews-r>=9` resolves to
`swift-t-r py313_3 + tk-8.6.13`; adding `tk>=8.6.15` flips it to
`swift-t-r py313_6 + tk-8.6.15` and the crash goes away.

Note the three published swift-t-r 1.6.9 osx-arm64 builds and their tk pins:
`_1.._3` -> `tk 8.6.13` (bad); `_4` -> `emews-r`, `tk>=8.6.15`;
`_5` -> `emews-r>=9`, `tk>=8.6.15`; `_6` -> `emews-r>=9`,
`tk>=8.6.15,<9.0a0`.  The solver will keep choosing an old `_3` as long as
anything upstream permits `tk 8.6.13`.

Fix (at the source, since we own eq-r): pin tk in eq-r's recipe
`EQ-R/<pyver>/conda/pkgs-tk.yaml`, `- tk` -> `- tk>=8.6.15` (floor only, NO
upper bound -- tk 9.0 is known to work per the 2026-10-13 Tcl 9 note above,
so we only need to exclude the broken 8.6.13), across the per-Python recipe
dirs (311-314; 310 was removed).  ALSO include `pkgs-tk.yaml` in the `run:`
section of each `meta-template.yaml`, not just `build:` -- it was build-only,
and the GitHub failure was an install-time (run:) solve.  A build-only pin
would rely on tk's `run_exports` to carry the floor into run deps; adding tk
explicitly to `run:` makes installed eq-r declare `tk>=8.6.15` directly, which
is what stops the install-time solver from picking tk 8.6.13 (matches the
"run: is a separate solve" lesson from the 2026-10-13 notes above).  Then
rebuild/upload eq-r.  This forces the solver onto a fixed swift-t-r build for
every consumer -- not just our installer.  (An installer-only stopgap is
adding `tk>=8.6.15` to the `conda install` line in `install_emews.sh`
alongside the note-17 `emews-r>=9` guard; the eq-r recipe fix is the real
one.)  EQ-R lives in a separate repo (`/Users/woz/proj/EQ-R`, outside this
working tree; per-Python recipe dirs 311-314).

=== 19a. m4 ate the tk pin: a comma in a comment is an arg separator

Platform: build-tooling (EQ-R m4 recipe); surfaces on any platform that
builds eq-r.

First attempt at note 19's fix silently failed: the rebuilt eq-r
(`py313_2`) shipped with NO tk dependency at all (not even the old
`tk >=8.6.13,<8.7.0a0`).  The `conda search --info` for `py313_2` listed
only `python`, `python_abi`, `swift-t-r 1.6.9`.

Root cause: `EQ-R/<pyver>/conda/common.m4` runs `m4_changecom(\`dnl')`, so
`#` is NOT an m4 comment -- `#` lines pass through as literal text but their
CONTENT is still live m4.  `pkgs-tk.yaml` is pulled in as the third argument
of `m4_ifelse(m4_getenv(USE_TK),\`1',m4_include(pkgs-tk.yaml))`.  A comment
line I added ended in a comma (`...version-agnostic),`).  m4 read that comma
as an ARGUMENT SEPARATOR inside `m4_ifelse(...)`, so everything after it --
the next comment line AND the actual `- tk>=8.6.15` line -- became a spurious
4th+ argument that `ifelse` discarded.  The include rendered as comments-only
with the pin gone (and no `pkgs-tk.yaml: STOP`, the tell-tale that m4
truncated the file mid-stream).

Debugged with `conda-build.sh -C` (configure-only: render meta.yaml and
stop) plus minimal m4 repro files kept in PWD (`313/conda/tmp-debug/`).
Bisection: each comment line passed alone, but the multi-line block with the
trailing comma dropped the tail -- confirming the comma, not any single word,
was the trigger.

Fix: remove ALL commas from the comments in `pkgs-tk.yaml` (all four recipe
dirs) and add an inline NOTE warning future editors.  Re-verified with
`conda-build.sh -C` that meta.yaml now renders `- tk>=8.6.15` in BOTH
`build:` and `run:`, each closed by `pkgs-tk.yaml: STOP`.  General rule for
these m4-included snippets: no commas (and mind parentheses) in `#` comments.

Caveat on the earlier "verification passed" (note 19): the dry-run solves
looked correct only because `swift-t-r py313_6` independently requires
`tk>=8.6.15`; the broken `eq-r py313_2` was contributing nothing.  Lesson:
verify the artifact's OWN metadata (`conda search --info` depends list), not
just the aggregate solve.

=== 19c. swift-t-r's tk `<9.0a0` ceiling is CORRECT -- do not loosen it

  tk 9.0.4 conflicts with any installable versions previously reported
----
The wall is NOT eq-r (its new pin is `tk >=8.6.15`, no ceiling).  It is
`swift-t-r py313_6`, which pins `tk >=8.6.15,<9.0a0`.  The effective stack tk
range is the intersection of all pins, so the `<9.0a0` ceiling wins.

Why the ceiling is right (first-reaction was wrong -- I called it
over-tightening; a user correction prompted this check): Swift/T's Turbine is
COMPILED and dynamically linked against a specific Tcl at build time.  The
published `libtclturbine.dylib` carries a load-time dependency on the exact
SONAME it was linked against -- `libtcl8.6.dylib` (confirmed in `gh.txt`:
`Symbol not found: _strstr ... Expected in: .../lib/libtcl8.6.dylib`).  Tcl 9
ships `libtcl9.0.dylib` (different SONAME) and `tclsh9.0`.  So dropping the
ceiling would let the solver install tcl 9.0 under a Turbine linked for 8.6
-> `dlopen` fails at load (Library not loaded), a different missing-lib but
the same class of crash as the strstr bug.  The `<9.0a0` pin enforces the
ABI contract between the installed tk and the tk that Turbine was built
against.

Reconciling with the "Tcl 9 works" note (2026-10-13): both are true.  Tcl 9
works IF Swift/T is BUILT against tcl 9 (`SPEC_TK=tk=9.0.4`, with the
version-agnostic TCLSH plumbing from that note).  It does NOT work by pinning
tcl 9 AFTER installing a swift-t-r that was built against 8.6 -- the link is
baked in.  The path to a Tcl-9 EMEWS stack is a MATCHED rebuild of swift-t-r
(and eq-r) against tcl 9, whose `run:` pin would then naturally be `tk >=9`;
NOT a user post-install pin against today's 8.6-linked builds.  Same
build-time-coupling principle as swift-t embedding `libpython3.XY` (note 14).

=== 19d. Enforcing the Tcl 9 exclusion in the recipes -- m4 comma handling

Platform: build-tooling (swift-t + eq-r m4 recipes); the Tcl-9 bound itself
is osx-arm64 (that is where SPEC_TK is set and where Turbine links libtcl8.6).

Acting on note 19c: added the `<9.0a0` upper bound to the tk spec at BOTH
layers so the exclusion is enforced by the recipes themselves, not left to a
coincidental swift-t-r pin.

Problem: the bound requires a comma (`tk>=8.6.15,<9.0a0`), which is exactly
the m4 argument-separator trap from note 19a.  Two layers needed different
handling because they source the tk spec differently:

* eq-r: `pkgs-tk.yaml` hardcodes the spec literally (no SPEC_TK var).  Fix is
  just to m4-quote the literal line: `` `    - tk>=8.6.15,<9.0a0' `` so the
  comma is inside one quote level.  Verified by `conda-build.sh -C` render in
  all four dirs (311-314).  No `common.m4` change -- the macro below is NOT
  needed in eq-r and was reverted there to avoid dead code.

* swift-t: `pkgs-tk.yaml` pulls the spec from an env var:
  `- m4_getenv(SPEC_TK)`.  Here the comma arrives only AFTER `m4_getenv`
  expands, so quoting the source line does not help -- the expansion happens
  inside the enclosing `m4_ifelse(...m4_include(pkgs-tk.yaml))` and the
  resulting comma splits that call's arguments.  Fix: a new comma-safe
  wrapper in `dev/conda/common.m4`:
----
m4_define(`_requote', ``$*'')dnl
m4_define(`m4_getenv_commas', `_requote(m4_esyscmd(printf -- "$`$1'"))')dnl
----
  m4 splits the expanded value on its comma into `$1,$2,...`, then `_requote`
  rejoins them with `` `$*' `` INSIDE one quote level, so the comma becomes
  literal text that the outer `m4_ifelse` does not see as a separator.
  `pkgs-tk.yaml` now calls `m4_getenv_commas(SPEC_TK)`, and
  `osx-arm64/deps.sh` sets `SPEC_TK='tk>=8.6.15,<9.0a0'`.

Why this macro and not m4 builtins: GNU M4 1.4.6 (the macOS `gm4`) in `-P`
mode does NOT expose `m4_dquote`/`m4_quote` as builtins -- they render
literally -- so the self-defined `_requote` is required.  Only the comma
needs handling; every other character valid in an Anaconda match-spec
(`> < = . | *` and digits) is m4-safe, so the wrapper deliberately does no
other escaping (user guidance).

Keep comment lines in these m4-included snippets comma-free AND free of macro
names: `#` is not an m4 comment here (changecom is `dnl`), so a word like
`m4_getenv` in a `#` line still expands (seen as a stray `$` in a first
render of the swift-t comment; reworded to avoid macro names).

Verified with `conda-build.sh -C`: osx-arm64 renders
`- tk>=8.6.15,<9.0a0` in `build:` and `host:` (run: inherits via
`pkgs-tk-run.yaml`'s `pin_compatible("tk")`); linux-64 (SPEC_TK defaults to
plain `tk`, no comma) still renders `- tk` correctly -- the wrapper is
backward-compatible with comma-free values.  Rebuild/upload swift-t to
publish the bound; eq-r is already fixed and published (note 19/19a).

== conda-build.sh provenance (CONDA_RELEASE_HASH/TIMESTAMP) and a forced
   "classic" solver hanging on GitHub Actions (2026-10-15)

=== 20. New feature: swift-t -v reports the release tarball's hash/timestamp

`conda-build.sh` now REQUIRES the `make-release-pkg.zsh` tarball
(`$DISTRO/swift-t-$SWIFT_T_VERSION/swift-t-$SWIFT_T_VERSION.tar.gz`) to exist
before building, aborting with "Run dev/release/make-release-pkg.zsh first!"
if not.  It md5sums that tarball and `zstat`s its mtime, exporting
`CONDA_RELEASE_HASH`/`CONDA_RELEASE_TIMESTAMP`, forwarded into the conda-build
sandbox via `meta-template.yaml`'s `script_env:` (plain env inheritance does
not happen for conda-build scripts).  `turbine/code/configure.ac`'s existing
`CONDA_BUILD` branch (the same mechanism that already produced the
`Anaconda-${CONDA_PY}_$DATE` `source.txt` token) now folds both values into
that single token instead of writing separate files:
`Anaconda_${CONDA_PY}_${CONDA_RELEASE_TIMESTAMP}_${CONDA_RELEASE_HASH}`, also
echoed via `AC_MSG_NOTICE` so it lands in `conda-build.log` too (`configure`
runs inside the `|& tee $LOG` block).  `turbine.in`'s `report_version()` was
NOT changed -- it already `cat`s `source.txt` for the `source:` line, so
`swift-t -v` picks up the new token for free.

Bug caught mid-edit: an earlier version of this change wrote the two values
to separate `conda-release-hash.txt`/`conda-release-timestamp.txt` files and
listed them in `turbine/code/Makefile.in`'s `PROVENANCE` var for
`install-etc` to `cp`.  When the session simplified to the single-token
`source.txt` approach, `configure.ac` stopped writing those two files but
`PROVENANCE` still named them -- `make install` would have failed on every
build (conda or not) with `cp: cannot stat 'conda-release-hash.txt'`.  Fixed
by reverting `PROVENANCE` to just `version.txt source.txt config.log`.
Lesson: when collapsing N generated files into fewer, grep every consumer
(here, the Makefile install rule) before trusting the simplification is
complete.

`checksum()` (`dev/conda/helpers.zsh`) was also tightened to match its actual
contract ("emit only the hash"): it used to pass through raw `md5sum`/`md5 -r`
output (`<hash>  -` on Linux, since it's fed via `<` redirection to suppress
the filename), which forced one caller
(`CONDA_RELEASE_HASH=${${(z)$(checksum ...)}[1]}`) to manually word-split and
take the first field.  Fixed `checksum()` itself to strip everything after
the first space (`${OUT%% *}`) before returning, so every caller (including
the pre-existing `conda-install.sh`/`conda-build.sh` PKG-metadata callers) now
gets a clean hash and the `(z)`-splitting workaround was removed.  The same
`${OUT%% *}` strip is applied uniformly after either branch (`md5 -r` on
`osx-*`, `md5sum` elsewhere), so it needs no platform-specific logic to also
cover macOS.

Verified end-to-end: ran `make-release-pkg.zsh` (full bootstrap, since
`configure.ac` changed) then `conda-build.sh linux-64 101`; `conda-build.log`
shows both the `meta.yaml` substitution and the `configure: CONDA_RELEASE_*`
`AC_MSG_NOTICE` lines, and the test-phase `swift-t -v` printed
`source:       Anaconda_311_2026-10-14_14:25_1d37c5e46627225e5f10a73fcc89035a`
-- the hash matches exactly what `make-release-pkg.zsh` printed for that
tarball.

=== 21. GitHub Actions PY=3.11 job hung ~4.5h solving the install env, then
    got killed by a runner shutdown -- not an unsatisfiable dependency set

`gh.txt` (OS=ubuntu-latest PY=3.11) showed `conda-install.sh`'s
`conda install --solver classic -c conda-forge ant gcc ncurses zsh autoconf
make mpich-mpicc=4.3.2 openjdk python=3.11 swig tk` fail both its fast
attempts (frozen solve, then `current_repodata.json`), fall back to solving

`##[error]The runner has received a shutdown signal` killed it.  No
`UnsatisfiableError`/`PackagesNotFoundError` ever appeared, and
`api.anaconda.org/package/conda-forge/mpich-mpicc/files` confirms
`mpich-mpicc=4.3.2` exists for `linux-64` -- so this was a solver

Root cause: `dev/auto-test/anaconda.sh`'s `CONDA_SOLVER` map forces
`-s classic` for PYTHON_VERSION=311 unconditionally, with the comment
"Jenkins cannot fall back to mamba here" -- a Jenkins-specific workaround
that was being applied to GitHub Actions too, even though GitHub Actions
runners support `libmamba` (conda's modern default) fine.

Fix: gate the `CONDA_SOLVER` lookup on `${GITHUB_ACTIONS:-false} == false`,
so Jenkins still forces `classic` for 311 but GitHub Actions lets conda pick
its own (libmamba) default:
----
if [[ ${GITHUB_ACTIONS:-false} == false &&
      ${CONDA_SOLVER[$PYTHON_VERSION]} != "default" ]] \
  USE_SOLVER=( -s ${CONDA_SOLVER[$PYTHON_VERSION]} )
----
Verified the gating logic in isolation (`zsh -c '...'` with
`GITHUB_ACTIONS=true` vs unset) picks the right branch in both cases.  Not
yet verified against a real GitHub Actions run (next PY=3.11 CI run should
confirm the install step no longer hangs).

build number *among otherwise-equal candidates*, but it is not required to

the SAME workflow run, OS=macOS-14 PY=3.11 passed while resolving to the

that particular tk-8.6.13 build hash happens not to trigger the `_strstr`
link bug (see the per-build-hash table in `osx-arm64/deps.sh`), so passing
is not proof of a clean resolve, and failing on py313 specifically is not
proof the fix didn't take -- both outcomes are solver-nondeterminism
artifacts of old builds remaining live.

Anaconda-313_2026-10-04_15-31`) -- so `swift-t -v`'s reporting itself is

metadata/hash corruption in play.

Lesson: publishing a fixed build number does not retroactively invalidate
older build numbers of the same version.  A spec like `eq-r=1.3` (version
only, no build floor) remains satisfiable by ANY build of that version
forever, including ones published before a known-bad dependency was
fixed.  Durable fix requires one of: (a) removing/yanking the broken old
builds from the channel (`anaconda remove`) -- done 2026-10-18, see
note 23; (b) tightening `install_emews.sh`'s install spec with an
explicit `tk>=8.6.15` floor so the solver can't reach the old
combination even if the old builds stay published; (c) bumping the
package *version* (not just build number) for fixes like this, so a
version floor in dependents structurally excludes old builds.  (a) was
chosen here as the immediate fix since it also cleans up the channel for
any pre-existing environments doing a fresh solve.
