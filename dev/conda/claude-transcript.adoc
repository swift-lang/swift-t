= Swift-T Conda glibc Fix — Session Transcript
:date: 2026-10-09

== Problem

Jenkins build failed at the `swift-t -E 'trace(42);'` test with:

----
couldn't load file ".../swift-t/turbine/lib/libtclturbine.so":
/lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.38' not found
(required by .../libtclturbine.so)
    while executing "load .../libtclturbine.so"
    ("package ifneeded turbine 1.5.2" script)
    invoked from within "package require turbine 1.5.0"
----

(The accompanying `libtinfow.so.6: no version information available` warnings
from zsh are a harmless symptom of the same conda-vs-host library mismatch,
not the failure.)

== Root cause

`libtclturbine.so` was *compiled* against the build host's **system glibc
(2.38)** instead of an older conda sysroot. When the built package is then
installed and tested on a host with glibc < 2.38, the dynamic loader cannot
resolve the `GLIBC_2.38` symbol versions, so the Tcl `load` fails and cascades
to `package require turbine`.

The recipe pulled in the bare `- gcc` metapackage, which does NOT reliably
activate a sysroot. The exact `GLIBC_2.38` requirement (the newest symbol
version on the builder) is the signature of "linked against the host libc".

This is the same class of problem as the GLIBCXX / libstdc++ issue the
project had already been fighting on GCE Jenkins
(see `dev/conda/conda-install.sh:139-148` and the "New Jenkins attempt" /
"Try plain GCC on Jenkins: 2026-10-09" changes).

== Recommended approach (conda, Linux)

Use the conda compiler-activation functions in the recipe rather than a bare
compiler metapackage:

[source,yaml]
----
requirements:
  build:
    - {{ compiler('c') }}
    - {{ compiler('cxx') }}
----

These expand to `gcc_linux-64` etc. and drag in `sysroot_linux-64`, setting
`CC`/`CFLAGS`/`CONDA_BUILD_SYSROOT` to the cos7 / glibc-2.17 sysroot. This is
the officially recommended idiom on BOTH conda-forge and Anaconda `defaults`.
Runtime libs (`libgcc-ng`/`libstdcxx-ng`) are added automatically via the
compilers' run-exports, so they belong in `build:` only, not `run:`.

Manually adding `gcc` + `sysroot_linux-64` is only a fallback for when the
jinja compiler functions cannot be used.

=== osx-arm64 note

macOS has no glibc; the equivalent portability floor is the **macOS SDK +
deployment target** (`LC_BUILD_VERSION` / `minos`), also provided by
`{{ compiler('c') }}` (which resolves to `clang_osx-arm64` there).

DECISION (this session): leave osx-arm64 as-is. Its `deps.sh` carefully pins
`clang==18.1.8` ("Prevent MPICH from updating Clang to 19") and documents the
`tk`/`strstr` two-level-namespace work. Switching to `{{ compiler() }}` would
drop the inline clang version pin (version would come from conda variant
pinnings) and risk regressing that work — and osx doesn't have the glibc bug
anyway. Fix applied to the gcc/linux path only.

=== zlib on osx-arm64 (verified unchanged)

USE_ZLIB resolution:

* `conda-build.sh:160` sets the default `USE_ZLIB=0`.
* `linux-64/deps.sh:8` overrides it to `1`.
* `osx-arm64/deps.sh` never sets it, so it stays `0`.

osx-arm64 therefore does NOT include `pkgs-zlib.yaml`, and never had zlib
before either: it has `USE_GCC=0`, and the old zlib entry lived *inside*
`pkgs-gcc.yaml` (which osx never pulled in). Confirmed:
`grep zlib osx-arm64/meta.yaml` returns nothing. Behavior identical before
and after the refactor.

Subtle improvement: the refactor made the gating MORE correct. Previously
zlib required BOTH `USE_GCC=1` AND `USE_ZLIB=1` (the inner `m4_ifelse` was
nested inside the gcc snippet). Now zlib is gated purely by `USE_ZLIB` — its
true meaning, decoupled from the compiler choice. Same result everywhere
today, but if osx-arm64 ever needs zlib you just set `USE_ZLIB=1` in its
`deps.sh` without touching the compiler path.

== m4 gotchas (snippet authoring)

These bit us while editing the pkgs-*.yaml snippets. Each snippet is pulled
into `meta-template.yaml` as the THIRD argument of `m4_ifelse(...)`:

  m4_ifelse(m4_getenv(USE_GCC), `1', m4_include(pkgs-gcc.yaml))m4_dnl

That context imposes two rules on snippet CONTENT (payload *and* comments):

1. NO COMMAS. A comma inside the included text is seen by m4 as an argument
   separator for `m4_ifelse`, so everything after the first comma is treated
   as excess arguments and dropped. Symptom seen this session:
     m4:.../meta-template.yaml:44: Warning: excess arguments to builtin
     `m4_ifelse' ignored
   The generated `meta.yaml` was truncated mid-comment, the `- {{ compiler(...) }}`
   lines were LOST, snippets ran together, and a literal `m4_dnl` leaked into
   the output. Fix: rewrote the comments in `pkgs-gcc.yaml` / `pkgs-zlib.yaml`
   to use ` -- ` and periods instead of commas. (The pre-existing snippets
   only worked because their comments happened to be comma-free.)

2. SINGLE QUOTES are m4 quote chars. Use DOUBLE quotes inside payload, e.g.
   `{{ compiler("c") }}` not `{{ compiler('c') }}`. Double quotes are valid
   jinja and pass through m4 untouched; a stray `'` unbalances m4 quoting.

Each snippet now carries a NOTE comment restating rule 1 so future edits do
not reintroduce the comma bug.

Verification that catches both: simulate the real inclusion rather than
filtering the snippet directly (direct filtering does NOT trigger the comma
bug because there is no enclosing m4_ifelse):

[source]
----
printf '%s\n' \
  'm4_ifelse(m4_getenv(USE_GCC),  `1'\'', m4_include(pkgs-gcc.yaml))m4_dnl' \
  'm4_ifelse(m4_getenv(USE_ZLIB), `1'\'', m4_include(pkgs-zlib.yaml))m4_dnl' \
  > /tmp/m4test.m4
USE_GCC=1 USE_ZLIB=1 m4 -P -I . common.m4 /tmp/m4test.m4   # expect: no warning
----

== Build flow (for reference)

`dev/auto-test/anaconda.sh` does two steps:

1. `conda-build.sh` (line 440) — compiles the package using `meta.yaml`.
   THIS is where `libtclturbine.so` gets its glibc requirement → the fix
   targets this step.
2. `conda-install.sh` (line 449) — installs the already-built package and
   runs `swift-t -E 'trace(42);'` (line 393), the test that failed.
   It does not recompile, so its `LIST+=( gcc )` is not the cause and does

   Once run-exports are in place, that manual `gcc` becomes redundant but
   harmless.

== Downstream fixes discovered while validating the build

Switching to the sysroot compilers let the build proceed far enough to
expose a chain of further issues (all pre-existing, surfaced by modern
conda-build's separate `_build_env`).  Each was fixed; the linux-64
`conda build` now passes end to end, including the test that originally
failed (`swift-t -E 'trace(42);'` -> `trace: 42`).

=== 4. mpicc exit 127 (stale cos6 backend)

`{{ compiler("c") }}` installs `x86_64-conda-linux-gnu-cc`, but the
`mpich-mpicc` wrapper defaulted to the stale `x86_64-conda_cos6-linux-gnu-cc`
backend (not installed) -> `command not found` -> exit 127.
FIX (`dev/conda/build-generic.sh`, linux branch): export
`MPICH_CC=${CC}` / `MPICH_CXX=${CXX}` (mirrors the osx-arm64 clang branch).

=== 5. MPI_IMPL=UNKNOWN (ancient mpich pulled)

Unpinned `mpich-mpicc` let the solver pull mpich 3.2.1, whose `mpi.h`
predates `MPICH_API_PUBLIC` - the only token Turbine's
`maint/mpi_identification.c` checks - so MPI detection failed:
`#error "Must specify MPI_IMPL!"`.
FIX (`dev/conda/linux-64/deps.sh`): `export SPEC_MPICH='mpich-mpicc=4.3.2'`
(4.x/5.x define `MPICH_API_PUBLIC`).  osx-arm64 already pins `mpich==4.1.2`.

=== 6. stc: Cannot run java! (baked build-env Java path)

`stc-config.sh` baked `USE_JAVA=$(which java)` = the build-env Java, and
its Conda re-resolution was gated on that path being MISSING - but
`conda build --dirty` keeps `_build_env` on disk, so the stale path
persisted and an unrunnable Java was used.  It also derived the prefix from
`${CONDA_EXE:h:h}` (the base env, which had no java) instead of the active
env.
FIX (`stc/code/etc/stc-config.sh`, SOURCE): under Conda, always resolve
Java from the active environment, in order: `$CONDA_PREFIX/bin/java`, then
`command -v java` (PATH), then the base env via `CONDA_EXE` incl. its
`pkgs/openjdk-*` cache; keep the build-time path only as last resort.
Result: `Using Java VM: $PREFIX/bin/java`.

=== 7. Baked build-env tool paths in turbine-config.sh (launcher/tclsh/python)

Installed `turbine-config.sh` baked `_build_env` paths for the launcher,
tclsh, mpicc and python.  The launcher was fatal (Turbine execs it):
`turbine/bin/turbine:362: no such file or directory: .../_build_env/bin/mpiexec`.
Root cause: those tools were only `build:` deps (-> `$BUILD_PREFIX`, which
Conda does NOT relocate and which is gone at run time).  Turbine's
`configure.ac` also `AC_CHECK_FILE`s the launcher, so it must exist at
build time - which, without a host prefix, forced the build-env path.
Separately, `libtclturbine.so` linked `libtcl8.6.so` but tcl was never a
declared dependency (conda-build warned the DSO was not found in packages).

FIX (the canonical conda build/host split):
* `dev/conda/meta-template.yaml`: added a `host:` section (python,
  openjdk, mpich, zlib, ncurses, tk, R) so these land in `$PREFIX` at
  build time and Conda relocates them into the install env.
* `dev/conda/settings.sed`: set `LAUNCHER=$PREFIX/bin/mpiexec` and
  `TCLSH=$PREFIX/bin/tclsh8.6` (the author's existing TODO) - now valid
  because the host section puts them in `$PREFIX`.
* `dev/conda/linux-64/deps.sh`: `USE_TK=1`, `SPEC_TK='tk'` to declare
  tcl/tk explicitly (tk provides `tclsh8.6` + `libtcl8.6.so`).
Result: `Using Turbine MPI launcher: $PREFIX/bin/mpiexec`, no missing-DSO
warning, test passes.  Package build string gains `py311` (correct: adding
python to host makes it a Python-ABI-specific build).

=== build/host/run distinction (why this works)

* build: tools run ON the build machine (compilers, make, ant) -> $BUILD_PREFIX, NOT relocated.
* host:  libs/tools linked/run against -> $PREFIX, present at build, Conda RELOCATES them.
* run:   what the user needs at runtime (often auto via run-exports).
Baked absolute paths are only relocatable when they point into the host
$PREFIX; anything in $BUILD_PREFIX (the `_build_env`) breaks at run time.

== 8. conda-install.sh: installed package failed to load (python ABI mismatch)

Installing the built PKG with `conda-install.sh` into a fresh env succeeded,
but running it failed:
  couldn't load libtclturbine.so: libpython3.11.so.1.0: cannot open shared
  object file
Cause: `conda-install.sh` had `SPEC_PYTHON="python"` (UNPINNED).  A fresh
env got Python 3.15, but the PKG is py311 (libtclturbine.so links
libpython3.11.so.1.0).  `conda install <file.conda>` does NOT enforce the
package's own python pin, so the mismatch slipped through.  libtcl8.6.so and
libmpi.so.12 were present (tk + mpich OK); only libpython was missing; the
RPATH (`$ORIGIN/../../../lib` = `$PREFIX/lib`) was correct.
FIX (`dev/conda/conda-install.sh`): derive the ABI from the PKG name
(`...-py311...` -> `python=3.11`) and pin SPEC_PYTHON to it.
RESULT: fresh-env install + `swift-t -E 'trace(42);'` -> `trace: 42`,
Python 3.11.17.  Validated end to end.

Note: conda-install.sh builds LIST without checking USE_ZLIB, so zlib is not
added explicitly (it came in transitively; harmless here).

=== 9. python-in-PATH warning (baked build-env python) - FIXED

The installed package printed:
  turbine: warning: python in PATH does not match the Python used at compile
  time   compiled with: .../_build_env   found in PATH: .../envs/.../bin/python
Turbine baked the build-env python DIRECTORY (TURBINE_USE_PYTHON).  Non-fatal
(the 3.11 ABI matches so libpython loads), but the same _build_env smell.

First attempt (`PYTHON_EXE=$PREFIX/bin/python` via `s@PYTHON_EXE=""@...@`) did
NOT work: `swift-t-settings.sh` has no uncommented `PYTHON_EXE=""` line to
anchor on (only commented examples), so the sed never matched.  Turbine's
configure then got `--enable-python` (not `--with-python-exe`) and
auto-detected `$BUILD_PREFIX/bin/python` (configure: `checking for python...
$BUILD_PREFIX/bin/python`).  The launcher/tclsh worked only because they were
appended after the matching `MPI_VERSION` anchor.

FIX (`dev/conda/settings.sed`): append PYTHON_EXE after the matching
ENABLE_PYTHON anchor:
  s@ENABLE_PYTHON=0@ENABLE_PYTHON=1\nPYTHON_EXE="$PREFIX/bin/python"@
Now build-turbine.sh passes `--with-python-exe=$PREFIX/bin/python`, turbine
bakes `$PREFIX/lib` (configure: `using Python: $PREFIX/lib python3.11`), and
Conda relocates it.  Validated on build 5: conda-build test has ZERO
python-mismatch warnings, and a fresh-env conda-install + `trace(42)` ->
`trace: 42` with no warning.

Lesson: settings.sed `s@VAR=""@...@` only works where swift-t-settings.sh has
that exact uncommented line; otherwise append after a known-present anchor
(ENABLE_PYTHON, MPI_VERSION).

Note: a stray `can't find package pt::pgen 1.0.3 (/usr/bin/pt)` appears at
runtime - that is a SYSTEM Tcl parser-tools binary on PATH, unrelated to the
package; `trace: 42` still succeeds (exit 0).  Benign.

== R-enabled build: RInside linked against the wrong R (2026-10-12)

`dev/conda/conda-build.sh -r 4.4 linux-64 4` (first time the `-r` /
`ENABLE_R` path was actually exercised) failed its test phase:

  couldn't load file ".../turbine/lib/libtclturbine.so":
  libRInside.so: cannot open shared object file: No such file or directory

Root cause: `r=VERSION` is listed in the `build:`, `host:`, and `run:`
sections of `pkgs-R.yaml`/`meta-template.yaml`. During the build,
`$BUILD_PREFIX/bin` is ahead of `$PREFIX/bin` on `PATH`, so any lookup that
just does `which R` / `which Rscript` silently resolves to the *build*
environment's R, not the host R that actually gets packaged/relocated.
Two separate places did this and both had to be fixed:

=== 9a. build-generic.sh RInside install - FIXED

`build-generic.sh` ran `which R` / `R RHOME` / `Rscript` to build and
`install.packages("RInside")` into whatever R that found. It found
`$BUILD_PREFIX/lib/R`, so RInside got compiled and installed into the
ephemeral build env -- discarded after the build, never shipped in the
package -- instead of the host `$PREFIX/lib/R` that ships and gets tested.

FIX: use `$PREFIX/bin/R` / `$PREFIX/bin/Rscript` explicitly instead of
`which`/bare `R`/`Rscript`, so RInside installs into the host R and is
packaged.

=== 9b. settings-R.sed R_INSTALL anchor - FIXED

Same anchor trap as the earlier `PYTHON_EXE` issue (9): `settings-R.sed` had
`s@R_INSTALL=.*@R_INSTALL="$R_HOME"@`, but `swift-t-settings.sh` has no
uncommented `R_INSTALL=` line to match (only a commented example), so the
substitution silently no-opped and `R_INSTALL` was never set. Without it,
`build-turbine.sh` passes `--enable-r` instead of `--with-r=$R_INSTALL`, and
turbine's `configure` finds R via plain `which Rscript` -- same
`$BUILD_PREFIX`-shadowing problem as 9a, this time baked into
`libtclturbine.so`'s link path.

FIX (`dev/conda/settings-R.sed`): append `R_INSTALL` after the `ENABLE_R`
anchor, like `PYTHON_EXE`:
  s@ENABLE_R=0@ENABLE_R=1\nR_INSTALL="$R_HOME"@
`$R_HOME` is exported by build-generic.sh (from `$PREFIX/bin/R RHOME`) and
expanded when `swift-t-settings.sh` is sourced at build time.

Both fixes were needed together -- fixing only 9a still left turbine's own
`configure` resolving R via `$BUILD_PREFIX`. Validated end-to-end on build 4:
`swift-t-r-1.6.9-py311r44h3fd9d12_4.conda` built, test phase prints
`trace: 42` with no `libRInside.so` error (the unrelated stray
`pt::pgen` message from note 9 still appears and is still benign).

Lesson: any "effective PATH / env var" anchor trick (`which TOOL`, an
`s@VAR=.*@...@` sed that depends on an uncommented line already existing)
should be treated as suspect wherever `$BUILD_PREFIX` and `$PREFIX` both
provide the same tool -- check both spots, not just the one that first
errors.

* dev/conda/settings-R.sed    (R_INSTALL appended after ENABLE_R anchor)

== conda-install.sh printf argument-collapsing bugs (2026-10-12)

`./conda-install.sh -r /tmp/.../broken/swift-t-r-...4.conda` reported
`size: 0.0 MB` instead of the real size.

=== 10a. msgf/failf "${*}" bug - FIXED

`msgf()`/`failf()` did `printf "${*}"`, which joins all arguments (format
string plus values) into ONE string before handing it to `printf`. With only
one argument left, `printf`'s `%s`/`%.1f` specifiers inside it have nothing to
consume and silently default to empty/`0` -- hence `size: 0.0 MB`.

FIX (`dev/conda/conda-install.sh`): use `"${@}"` instead of `"${*}"` in both
`msgf` and `failf`, preserving the format string and each value as separate
`printf` arguments. Verified: re-running the same command now correctly
prints `size: 8.3 MB`.

=== 10b. abortf() same bug pattern - FIXED (latent, no bad caller yet)

`turbine/code/scripts/helpers.zsh`'s `abortf()` had the identical pattern,
worse: it also pre-split `${*}` into an array (`local MSG=( ${*} )`), which
further breaks on any value containing a space. No current caller passes a
space-containing value, so this was latent, but the same fix was applied
proactively:

  printf "$@"

(`"$@"` and `"${@}"` are equivalent in zsh.) Verified directly:
`abortf "value: %s end: %s\n" "has a space" "ok"` now correctly prints
`value: has a space end: ok` and exits 1.

=== 10c. CONDA_PLATFORM auto-detect from conda-bld/broken/ - FIXED

Following directly from the bug above: once `size:` was fixed, the same
command failed one step later with a confusing
`no such file or directory: .../conda/broken/deps.sh`. `CONDA_PLATFORM` is
auto-detected from `PKG`'s parent directory name (`${PKG:h:t}`), so pointing
`PKG` at a copy left in `conda-bld/broken/` sets `CONDA_PLATFORM=broken`
instead of a real platform.

FIX (`dev/conda/conda-install.sh`): added an early, explicit check right
after `CONDA_PLATFORM` is determined -- if `$DEV_CONDA/$CONDA_PLATFORM/deps.sh`
doesn't exist, fail immediately with a clear message (special-cased for the
`broken/` case) telling the user to pass `-P PLATFORM` instead of letting it
fail later inside `source`.

Files changed this session:
* dev/conda/conda-install.sh       (msgf/failf "${@}"; CONDA_PLATFORM validation)
* turbine/code/scripts/helpers.zsh (abortf "$@")

=== 11a. Stale conda package-cache entry masked the fix - gotcha, not a bug

First attempt still failed with the exact same `libRInside.so` error, and
`swift-t -v` printed the OLD (broken) build's internal path
(`.../swift-t-r_1791832943271/_build_env/lib/R`). Root cause: the BROKEN and
FIXED `.conda` files share the identical filename
(`swift-t-r-1.6.9-py311r44h3fd9d12_4.conda`, both built with `BUILD_NUMBER=4`
during this session's rebuild iterations). Conda's `pkgs_dirs` cache
(`/usb3/woz/conda-cache`, from `conda config --show pkgs_dirs`) keys cached
EXTRACTED packages by filename/name-version-build, not content hash, so it
silently reused the stale extraction from the earlier broken-package install.
Separately, conda also considered the package "already installed" in
`/tmp/woz/311-T` (same name/version/build spec) and skipped reinstalling even
after the shared cache was cleared -- `conda remove -p /tmp/woz/311-T
swift-t-r` was needed before the fixed package would actually be
re-extracted/re-linked.

Lesson: when iterating conda-build with a fixed `BUILD_NUMBER`, a stale
package-cache (`pkgs_dirs`) or stale "already installed" env state can make a
real fix look like it didn't work. Bump `BUILD_NUMBER`, or
`conda remove`+clear the cache entry, when re-testing a fix under the same
version/build string.

Verified end-to-end: `swift-t -v` in `/tmp/woz/311-T` reports
`source: Anaconda-311_2026-10-12_14-58` (the fixed build) and
`swift-t -E 'trace(42);'` prints `trace: 42` with no `libRInside.so` error.

=== 11b. pt::pgen warning - FIXED (was wrongly called "benign/unrelated" in note 9)

Note 9 said the `can't find package pt::pgen 1.0.3 (/usr/bin/pt)` warning was
a benign, unrelated system binary. Tracing it with `strace -f -e
trace=execve` during a `swift-t -E 'trace(42);'` run showed it is NOT
spurious noise -- it is `pt -d` being exec'd as a real subprocess, from
`turbine/bin/turbine` (and, before 9's shebang hygiene existed, from
`swift-t`/`stc` too). `pt` is a personal zsh shell function (temp-file
tracking/cleanup, `-d` = delete) defined via this developer's own
`~/.zshenv`/`~/.zshrc`. `bin/swift-t`, `bin/stc`, and `bin/turbine.in` all had
shebang `#!/usr/bin/env zsh` (no `-f`), so they source the invoking user's
rc files; the `pt` shell function from those rc files never gets installed in
a plain `zsh` invocation inside a non-interactive script (no `.zshrc` is
sourced there either), so the exit-trap-driven `pt -d` falls through PATH to
the unrelated system `/usr/bin/pt` (a tcllib Tcl parser-generator script,
`package require pt::pgen`), which fails because that tcllib package isn't
installed in the conda Tcl.

This is a real cross-user footgun: ANY developer with a personal shell
function/trap named `pt` (or any other name colliding with a system binary)
sees this warning, and it's not obviously caused by Swift/T.

FIX: give `swift-t`, `stc`, and `turbine` clean, rc-isolated shells, like
`dev/conda/conda-install.sh` already does (`#!/bin/zsh -f`):
* `stc/code/bin/swift-t`      : `#!/usr/bin/env zsh` -> `#!/usr/bin/env -S zsh -f`
* `stc/code/bin/stc`          : `#!/usr/bin/env zsh` -> `#!/usr/bin/env -S zsh -f`
* `turbine/code/bin/turbine.in`: `#!/usr/bin/env zsh` -> `#!/usr/bin/env -S zsh -f`
(`env -S` splits the one argument into `zsh -f`; needed because `#!` only
passes a single argument to the interpreter.)

Verified by patching the installed copies in `/tmp/woz/311-T` and re-running
`swift-t -E 'trace(42);'`: the `pt::pgen` warning no longer appears anywhere
in the output; `trace: 42` prints cleanly.

* stc/code/bin/swift-t          (shebang -> zsh -f)
* stc/code/bin/stc              (shebang -> zsh -f)
* turbine/code/bin/turbine.in   (shebang -> zsh -f)

== Stale distro snapshot masked the shebang fix in a real package build (2026-10-12)

After note 11b's shebang fix was verified by hand-patching the INSTALLED
scripts in `/tmp/woz/311-T`, a real rebuild (`conda-build.sh -r 4.4 linux-64
6`) was made to ship the fix properly. First attempt used `BUILD_NUMBER=5`;
the resulting package installed cleanly but `swift-t -v` STILL printed the
`pt::pgen` warning, and `head -1` on the freshly-installed `bin/swift-t`,
`bin/stc`, `turbine/bin/turbine` showed the OLD `#!/usr/bin/env zsh` shebang
-- i.e. the git-tracked source fix had not made it into the built package at
all.

Root cause: `conda-build.sh` does not build from the live git working tree.
Its recipe source is `$TMP/distro` (`meta-template.yaml`'s
`source: path: m4_getenv(DISTRO)/...`), a SNAPSHOT directory produced ahead
of time by `dev/release/make-release-pkg.zsh`, which copies files with
`cp -u --parents` (copy only if the source is newer than the existing
destination). An old `/tmp/distro` snapshot from an earlier (pre-fix) session
already existed with its own file timestamps; depending on exactly how/when
the three shebang edits were made, `cp -u` evidently judged the snapshot
copies already up to date and skipped re-copying them, so the fix silently
never reached the build input. Build 5 then rebuilt and reinstalled a
perfectly reproducible package -- just one still carrying the unfixed
shebangs.

FIX / correct procedure:
1. `rm -rf /tmp/distro` (the snapshot is pure build scratch, not source) and
   regenerate it fresh: `dev/release/make-release-pkg.zsh -b -T` (`-b` skips
   the autotools bootstrap since no configure.ac/Makefile.am changed; `-T`
   skips making a tar.gz, the plain `$TMP/distro/swift-t-VERSION/swift-t-VERSION`
   directory is all `conda-build` needs). Verified the regenerated snapshot's
   `bin/swift-t`/`bin/stc`/`turbine.in` now show `#!/usr/bin/env -S zsh -f`.
2. Clear only the affected conda package-cache entries (same class of issue
   as note 11a, but now hitting the SOURCE side instead of the install side):
   removed the stale `swift-t-r-1.6.9-py311r44h3fd9d12_{4,5}` and
   `swift-t-1.6.9-py311h3fd9d12_{4,5}` directories/`.conda` files from
   `/usb3/woz/conda-cache` (`conda config --show pkgs_dirs`), leaving all
   other cached versions/builds untouched.
3. Rebuilt as `BUILD_NUMBER=6` (`conda-build.sh -r 4.4 linux-64 6`) from the
   regenerated distro -- new build number again avoids any residual
   name/version/build collision, per note 11a's lesson.
4. Installed into `/tmp/woz/311-T` via `conda-install.sh -r
   swift-t-r-1.6.9-py311r44h3fd9d12_6.conda`.

Verified end-to-end: installed `bin/swift-t`/`bin/stc`/`turbine/bin/turbine`
all show `#!/usr/bin/env -S zsh -f`; `swift-t -v` prints cleanly with NO
`pt::pgen` warning; `swift-t -E 'trace(42);'` prints only `trace: 42`.

Lesson: `conda-build.sh` is TWO HOPS removed from the git working tree
(working tree -> `$TMP/distro` snapshot via `cp -u` -> conda-build recipe
source). A source-tree edit is not guaranteed to reach a build just by
re-running `conda-build.sh` with a new `BUILD_NUMBER` -- the distro snapshot
must also be known-fresh (either regenerated, or confirmed newer than the
snapshot by `cp -u`'s timestamp comparison). When a fix mysteriously doesn't
show up in a rebuilt package, check `head -1`/diff the actual files under
`$TMP/distro/.../<path>` against the git source before assuming the build or
install step is broken.
